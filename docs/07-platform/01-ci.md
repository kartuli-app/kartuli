# CI

`.github/workflows/staging-orchestrator.yml` runs on PRs to `main` and manual dispatch. It calls `scripts/orchestrator/detect-affected.mjs --pr` and `map-affected-to-workflows.mjs`, using the target mapping under `scripts/orchestrator`, to select reusable jobs.

| Selected surface | Reusable workflow |
| --- | --- |
| Next.js apps | `staging-w-app-nextjs.yml`, matrix of affected targets and `local` / `vercel` deployment targets |
| Web Docs | `staging-w-tool-web-docs-client.yml` |
| Storybook | `staging-w-tool-storybook.yml` |

The orchestrator also runs all-monorepo validation independently of affected target selection. `ci-setup-node` installs pinned pnpm/Node, restores caches and uses `pnpm install --frozen-lockfile`. `ci-validate-all-monorepo` and `ci-validate-monorepo-package` centralize validation. [Testing](../06-quality/01-testing/index.md) owns the test strategy.

## Pull-request execution flow

1. `detect-affected` checks out full history, installs dependencies and asks Turbo for affected `build`
   tasks against a freshly fetched `origin/main`.
2. The mapper reads a JSON array on stdin and maps full workspace names through
   `workflow-targets.json`. It writes Next.js, Web Docs and Storybook matrices plus a job summary.
3. Each nonempty bucket calls its reusable workflow. Next.js targets run both a local-build/server path
   and a Vercel-preview path; each runs Lighthouse and its target Playwright suite.
4. `validate-all-monorepo` runs regardless of the affected buckets. It validates documentation and
   navigation through the Web Docs workspace test, executes root lint, installs
   Chromium, then runs typecheck, workspace lint, V8 coverage and Storybook browser tests in parallel.
   It does not call Turbo `test:all`; Web Docs tests are invoked explicitly before the parallel tasks.

The package-level validation action runs only on manual dispatch inside the reusable staging workflows;
normal orchestrated PR runs rely on the independent all-monorepo job plus each target's build/E2E path.
The Web Docs build also runs source validation and navigation tests before rendering, then checks
the built index. Its Playwright suite checks rendered delivery separately.

## Reproducing affected selection

From the repository root with network access to refresh `origin/main`:

```bash
pnpm run orchestrator:detect-affected:pr
pnpm run orchestrator:detect-affected:pr | \
  node scripts/orchestrator/map-affected-to-workflows.mjs
```

The first command prints a JSON array of workspaces with a real `build` task in Turbo's affected graph.
The second prints the mapped object. The mapper accepts no command-line arguments and loads only its
colocated `workflow-targets.json`. An affected workspace can be valid yet unmapped; inspect the
`unmapped` result before assuming a missing job is a Turbo failure.

## Failure diagnosis

Start with the first failing job/step and determine whether it is detection, setup/install, static
validation, build/server readiness, deployment, Lighthouse or Playwright. A later artifact/comment can
exist even when another parallel task failed. For cache-related surprises, inspect the Turbo dry run and
task inputs; for a missing target job, inspect workspace scripts/dependency edges and the mapper config.

CI uses the pinned `.nvmrc`, root `packageManager` and frozen lockfile. Reproduce with those versions
before changing code to accommodate a different local runtime. Browser or DNS failures are environment
failures until a code/config cause is demonstrated.

Concurrency cancels earlier runs for the same PR. The automatic diagram commit job is commented out. App staging jobs can post preview comments and send notifications; workflows explicitly scope permissions.

This page records current YAML behavior. Branch-required checks, app installation permissions and GitHub environment approvals require [manual verification](../10-services/01-github.md). Production path filters and workflow deduplication are follow-up concerns, not changes in this documentation foundation.
